# Goal 6: simulated evaluation (smoke test)

> **This is not a system evaluation.** Every signal in it is generated by `np.random.normal`, and the headline scores are forced by how far apart the generator puts healthy and faulty values. Live-telemetry results are in [`RESULTS_LIVE.md`](RESULTS_LIVE.md) and summarised in [`final_report.md`](final_report.md).
>
> The script still runs as a quick check that the particle filter and the metric code work end to end: `python scripts/36_evaluate_goal6.py --source synthetic`.

## What it does

1. **Parameters** come from Goal 5, which samples 2,000 ticks of hidden states and anomaly scores from a hand-written generator (`true_mu = [0.1, 3.0, 5.5]`) and fits them with `DBNParameterLearner`. Because the data comes from a known generator, this recovers that generator's values: a valid test of the estimator, but not calibration from telemetry.
2. **Trials:** 100 simulated runs of 30 ticks on a four-service star topology, in which `ts-ui-dashboard` is the parent of `ts-train-service`, `ts-route-service` and `ts-order-service`.
   - 50 healthy trials: every service emits `max(0, N(0.1, 0.1))`.
   - 50 fault trials: from tick 15 the injected service emits `N(5.0, 0.5)`, the dashboard emits `N(1.5, 0.5)`, and the rest stay healthy.
3. **Alarm:** any service with `P(Critical) > 0.5`.

## Result

| Metric | Result |
|---|---|
| True positives / false negatives | 50 / 0 |
| False positives / true negatives | 0 / 50 |
| Precision, recall, F1 | 100% |
| False positive rate | 0% |
| Detection latency | 1.74 ticks |
| Root-cause accuracy | 44% (22 of 50) |

## Why these numbers say little about the system

**Detection is forced to 100%.** Healthy signals sit at 0.1 ± 0.1 and faulty ones at 5.0 ± 0.5, about ten standard deviations apart even measured against the wider distribution. Any threshold between 0.5 and 4.0 separates them perfectly, so perfect precision and recall show only that the code runs.

**The 44% root-cause score is a topology artefact.** The breakdown shows every wrong answer was the same:

| Injected | Correct | Blamed the UI dashboard |
|---|---|---|
| ts-order-service | 10 | 12 |
| ts-route-service | 6 | 12 |
| ts-train-service | 6 | 4 |
| **Total** | **22** | **28** |

All 28 errors blamed `ts-ui-dashboard`. In a flat star the dashboard is the parent of every candidate and itself has no parent, so whenever its degraded signal pushed it towards Critical it looked like the upstream-most failure. An earlier version of this document attributed the errors to probability "bleeding" through the learned transition matrix; the single blamed service points to the graph shape instead.

The shape matters in practice. With the same simulated signals, a flat star topology scored 60% root-cause accuracy and the service graph discovered from live traffic (which has depth) scored 100%, on 5 fault runs. On live telemetry with the discovered graph, root cause was correct on 3 of 3 faults.
